# Description
CVEScannerV2 combines an Nmap NSE script for vulnerability discovery with a
Python package that builds and queries the SQLite CVE database.

# Technical details
The current implementation take care of the following cases:

- If Nmap detects:
  - `cpe` **AND** `version`: vulnerabilities affecting `version` and
    vulnerabilities affecting a range of versions that include `version`.
  - `cpe` **AND** `version range`: vulnerabilities affecting versions
    between `version range` (included).
  - `cpe` but **NO** `version`: vulnerabilities that affect
    every version of the product.
  - HTTP fingerprints supplement Nmap's CPE and version detection on HTTP,
    SSL and UPnP ports.

- HTTP detection:
  - Used only if port matches **HTTP**/**SSL**/**UPnP**.
  - On first use, the script downloads the latest `index.json`,
    `fingerprints.json`, `paths.json` and `probes.json` from the upstream
    `nmap-vulners` catalogue and caches them in the root `data/` directory.
    Later runs reuse those files. It checks responses from catalogue paths,
    including headers, body, title, meta tags, script sources and cookies.
    Nmap service fingerprints are checked too.
  - A targeted probe runs only after its product detector matches and no
    version was found. Requests are pipelined in batches paced according to
    Nmap's timing template.
  - If the upstream catalogue cannot be fetched on first use, the script
    falls back to legacy JSON files when present. Cached catalogues remain
    available offline. Nmap CPE detection works without either source.

> Nmap library shortport is used to detect if port matches HTTP/SSL.

# Project architecture
The repository has two runtime components:

- `cvescannerv2.nse` scans discovered services and reads CVE data from SQLite.
- `db-manager/` is a Python package that updates and queries that database.

The database package separates command-line and Textual interfaces, application
workflows, domain data and CPE parsing, and infrastructure adapters for NVD,
Metasploit, Exploit-DB, HTTP, and SQLite. See the
[`db-manager` guide](db-manager/README.md) for its architecture and workflows.

# Requirements
Run commands from the repository root. The scanner requires the CVE database
at `data/cve.db` by default.

HTTP fingerprinting downloads the latest upstream catalogue on first use and
stores it in the root `data/` directory. The database and downloaded catalogue
files are excluded from version control. Delete the four catalogue JSON files
and `data/.vulners-catalog-source` to download the latest catalogue again.
Legacy paths and regex files are optional fallbacks. Product aliases are
stored in `data/product-aliases.json`. In addition, install `lua-sql-sqlite3`
(Ubuntu) or `lua5.4-sql-sqlite3` (Alpine).

## Optional
If you don't have the database `data/cve.db`, you can build it
using the `db-manager` command or download a (semiupdated) copy
from [CVEScannerV2DB](https://github.com/scmanjarrez/CVEScannerV2DB) using `.sql` files
or under Actions->Latest->Summary->Artifacts

> This repository is updated every two weeks

```bash
uv sync --project db-manager
uv run --project db-manager db-manager
```
The current importer only associates CVEs with NVD CPE entries marked
`vulnerable: true`. Databases generated by older versions may contain
supporting platform entries as affected products. Build a fresh database
after upgrading the importer. Use a new path to keep the old file:

```bash
uv run --project db-manager db-manager --database data/cve-clean.db
nmap -sV --script cvescannerv2 --script-args db=data/cve-clean.db <target>
```

Updates rebuild records modified by NVD since the saved timestamp. Long gaps
are split into date ranges shorter than NVD's 120-day maximum. If the saved
timestamp is missing, invalid, or in the future, the importer refreshes all
records.

Interrupted downloads resume automatically when you run the same command
against the same database. SQLite stores the original query windows and a
checkpoint for each page, committed in the same transaction as its records.
The progress bar starts with the committed pages already counted; incomplete
or failed pages are downloaded again. If reference downloads fail after NVD
finishes, retrying also preserves all completed NVD pages.

NVD uses live offset pagination, not immutable page snapshots. On resumption,
the importer checks fresh result counts. For a growing full catalogue it
retains the contiguous prefix of complete pages and retries gaps and the old
partial tail. A smaller catalogue or a changed filtered result count causes
that collection to be fetched again because its offsets may have shifted.
The original synchronization cutoff is retained so subsequent incremental
updates include changes made during the interruption.

Downloads interrupted before checkpoint support was installed must fetch
their pages once more: existing product rows alone cannot identify which
API pages were completely imported. Existing databases gain the checkpoint
tables automatically; no database deletion or extra CLI option is needed.

NVD pages are validated and processed asynchronously. CVE changes and their
product associations go through a typed queue to a batched SQLite writer. On
incremental updates, each changed CVE is removed before its current data and
associations are rebuilt. The updater then refreshes Metasploit references and
optionally scrapes Exploit-DB titles. Pass `--noscrape` to skip title requests.

```bash
git clone https://github.com/scmanjarrez/CVEScannerV2DB
cd CVEScannerV2DB && sh build.sh
```

> **Note:** In order to run `db-manager`, you need to
> [request an API key](https://nvd.nist.gov/developers/request-an-api-key)
> and save it to a file named `.api` on your current working directory
> or in the environment variable `NVD_KEY`.

The importer uses asynchronous HTTP requests. NVD request starts are spaced
at least 0.75 seconds apart, with at most four requests in flight. Metasploit
requests are spaced by one second, and Exploit-DB scraping by two seconds with
at most three requests in flight. HTTP 429 and selected server errors are
retried up to three times; the importer honors `Retry-After` when provided.

# Execution
To run the script, use the following syntax
```
nmap -sV --script cvescannerv2 <TARGET>
nmap -sV --script cvescannerv2 --script-args log=logfile.log,json=logfile.json <TARGET>
```

It is possible to modify the behaviour using the following arguments: db,
maxcve, http, maxredirect, log, json, catalog, catalog_url, path, regex,
aliases, service, version, smb and minconf.
<details>
    <summary><b>script-args default values</b></summary>

    db: data/cve.db
    maxcve: 10
    http: 1
    maxredirect: 1
    log: cvescannerv2.log
    json: cvescannerv2.json
    catalog: auto
    catalog_url: https://raw.githubusercontent.com/vulnersCom/nmap-vulners/catalog/
    path: data/http-paths-vulnerscom.json (legacy fallback)
    regex: data/http-regex-vulnerscom.json (legacy fallback)
    aliases: data/product-aliases.json
    service: all
    version: all
    smb: 1
    minconf: low
</details>

<details>
    <summary><b>script-args examples</b></summary>

    nmap -sV --script cvescannerv2 --script-args db=data/cve.db <TARGET>
    nmap -sV --script cvescannerv2 --script-args maxcve=5 <TARGET>

    # Change reports path
    nmap -sV --script cvescannerv2 --script-args log=scan2023.log,json=scan2023.json <TARGET>

    # Only scan certain service/version
    nmap -sV --script cvescannerv2 --script-args service=http_server,version=2.4.57 <TARGET>

    # Disable HTTP detection
    nmap -sV --script cvescannerv2 --script-args http=0 <TARGET>

    # Disable remote and legacy HTTP fingerprint catalogues
    nmap -sV --script cvescannerv2 --script-args catalog=none <TARGET>

    # Use a local mirror of the upstream catalogue
    nmap -sV --script cvescannerv2 --script-args catalog_url=http://127.0.0.1:8000/ <TARGET>

    # Disable the SMB probe used to get the exact Samba version
    nmap -sV --script cvescannerv2 --script-args smb=0 <TARGET>

    # Show only medium and high confidence results in table and log
    nmap -sV --script cvescannerv2 --script-args minconf=medium <TARGET>
</details>

> **Note**: `cvescannerv2.nse` can be placed in Nmap default script directory
> for global execution.
>
> - Linux and OSX default script locations:
>   - /usr/local/share/nmap/scripts/
>   - /usr/share/nmap/scripts/
>   - /opt/local/share/nmap/scripts/
>   - /usr/local/Cellar/nmap/<i>&lt;version&gt;</i>/share/nmap/scripts/
>
> - Windows default script locations:
>   - C:\Program Files\Nmap\Scripts
>   - %APPDATA%\nmap
>
> It's recommended to create a **symbolic link**, so changes in repository are reflected
> in the script.

## Output
CVEScannerV2 will show CVEs related to every `service-version` discovered.
> **Note**: This script depends on heuristics implemented in Nmap, so if it doesn't
> detect a service or is detected incorrectly, CVEScannerV2 will show an incorrect output.

Each service row includes a `Conf` column with the confidence level of its
CVE matches (`high`, `medium` or `low`, see [Confidence levels](#confidence-levels)).
The service header shows the `version_source` used to obtain the version.
When the version comes from a distribution package that may contain a
backported fix, a `distro_backport` warning is shown, because the upstream
version alone may not reflect the patch level.

The JSON log adds the following fields: `confidence`, `reasons`,
`version_source`, `os_context`, `warnings` and `summary`.

> **Note**: The table layout changed to include the `Conf` column.

# Confidence levels
Each CVE match receives a confidence level based on the evidence that produced
it. The level of a result is the lowest level among all its reasons.

| Level  | Meaning                                                              |
|--------|----------------------------------------------------------------------|
| high   | The version matches directly and the evidence is unambiguous.       |
| medium | The match depends on a range, a version series or an unverified condition. |
| low    | The match relies on weak evidence, an unbounded or observed range, or a platform mismatch. |

Reasons that can appear in the `reasons` field:

| Reason                    | Description                                              |
|---------------------------|----------------------------------------------------------|
| `exact_version`           | The detected version equals the affected version.       |
| `range_contains`          | The detected version lies inside the affected range.    |
| `range_overlap`           | The detected version overlaps the affected range.       |
| `series_expanded`         | The version was expanded to its release series.         |
| `update_unknown`          | The update level is unknown.                            |
| `requires_platform`       | The CVE applies only on a specific platform.            |
| `requires_component`      | The CVE applies only when a specific component is present. |
| `nvd_unbounded`           | NVD gives no bound for the affected range.              |
| `observed_range`          | Nmap reported a broad version range (for example 3.X - 4.X).   |
| `platform_mismatch:<family or distro>` | The detected platform differs from the one the CVE requires (family, or distro vendor when only the distro differs). |

# Nmap detection limitations
The Nmap-based detection has limits that the script cannot overcome:

- It cannot confirm that a CVE is exploitable on the target.
- It cannot see the configuration of the service, so a vulnerable version may
  not be reachable or exposed.
- It cannot tell which Metasploit or exploit modules are active or applicable.
- A CVE whose affected configuration requires several applications (AND) cannot
  be fully checked when one of those applications is not detected.

Platform conditions require a database built with the new `db-manager`
version. A database built with an older version does not contain these
conditions, so they are skipped and a warning is shown.

# Errors and fixes
## Upstream request failures
The updater retries HTTP 429 and selected server errors up to three times and
honors `Retry-After`. If a request still fails, check network access and the
upstream service before running the update again. The NVD synchronization
timestamp is saved after the update completes, so a failed run can retry the
same update window.

## Missing luasql
> cvescannerv2.nse:54: module 'luasql.sqlite3' not found:<br>
> NSE failed to find nselib/luasql/sqlite3.lua in search paths.<br>
> ...

**Fix:** Install the library based on your OS (check [Requirements](#requirements))
and create a symlink to Nmap search path.
```bash
apt install lua-sql-sqlite3
ln -s /usr/lib/x86_64-linux-gnu/lua /usr/local/lib/lua
```

```bash
apk add --no-cache lua5.4-sql-sqlite3
ln -s /usr/lib/lua /usr/local/lib/lua
```
> Above commands may require super user permissions.

# Docker container
The multi-stage Docker build publishes two `scratch` images. The `db` target
contains the latest database built from the `CVEScannerV2DB` dump repository;
the `nodb` target omits it. Both images contain only Nmap, its runtime
dependencies, the NSE script, and the product aliases.

- Database embedded version: `scmanjarrez/cvescanner:db` or
  `scmanjarrez/cvescanner:latest`
- No database: `scmanjarrez/cvescanner:nodb`

On a release, the workflow also publishes the Git tag for the database image
and the same tag with `-nodb` appended for the lightweight image. For example,
release tag `v4.0` publishes `v4.0` and `v4.0-nodb`.

```bash
docker run -v /tmp/cvslogs:/tmp/cvslogs scmanjarrez/cvescanner:db \
  --script-args log=/tmp/cvslogs/scan.log,json=/tmp/cvslogs/scan.json <TARGET>

docker run -v "$PWD/data:/CVEScannerV2/data" \
  -v /tmp/cvslogs:/tmp/cvslogs scmanjarrez/cvescanner:nodb \
  --script-args log=/tmp/cvslogs/scan.log,json=/tmp/cvslogs/scan.json \
  <TARGET>
```

Build either target locally with Docker Buildx:

```bash
docker buildx build --load --target nodb \
  -t scmanjarrez/cvescanner:nodb .
docker buildx build --load --target db \
  --build-arg DATABASE_REFRESH="$(date +%s)" \
  -t scmanjarrez/cvescanner:db .
```

Nmap dependencies, the upstream database, and scanner source assets are built
in independent stages. APK downloads use a cache mount per architecture, and
`COPY --link` keeps the large runtime and database layers reusable when only
the NSE script, aliases, or license change. The build context includes only
the scanner runtime assets; local databases, virtual environments, results,
and API keys are excluded. Product aliases remain in version control.

Keep `DATABASE_REFRESH` unchanged to reuse the database build. Change it to
fetch a new upstream snapshot; the release workflow does this automatically.
BuildKit is required for the cache mounts and linked copies.

> **Note**: You can find your logs in `/tmp/cvslogs` directory

# Query database
The `db-query` command opens an interactive Textual interface when run without
`--product`. It suggests product names from the selected database and displays
exact-version and version-range matches in separate tables. Press the right
arrow to accept a product suggestion, then press Enter or select Search.

Exact versions are compared by their dotted version components. Range results
respect NVD's inclusive and exclusive start and end bounds. Use `--raw` to
include unfiltered database rows alongside the filtered matches.

```bash
uv run --project db-manager db-query
uv run --project db-manager db-query --interactive
```

For a one-off query, pass the product and optional version filters:

```bash
uv run --project db-manager db-query --help
uv run --project db-manager db-query -p "gibbon" -v "25.0.0"
```

# Regression checks
Run these checks from the repository root (Lua 5.4 is required for the scanner
tests). They use temporary SQLite databases and mocked external services:

```bash
PYTHONPATH=db-manager/src uv run --project db-manager \
  python -m unittest discover -s db-manager/tests -v
lua5.4 tests/test_scanner.lua
```
