# Scanner tests

Tests for `cvescannerv2.nse` that do not need Nmap. The NSE libraries
(`http`, `nmap`, `stdnse`, `shortport`, `json`, `lfs`, `datetime`) are
replaced with stubs, and the database is a temporary SQLite fixture.

## Container execution (recommended)

```bash
docker build -f nmap/tests/Dockerfile -t cvescannerv2-tests .
```

```bash
docker run --rm cvescannerv2-tests
```

To test local code without rebuilding the image:

```bash
docker run --rm -v "$PWD:/src:ro" cvescannerv2-tests
```

`nmap/tests/Dockerfile.dockerignore` defines the context of this image. The
root `.dockerignore` is not modified, and the scanner image does not include
`nmap/tests/`.

## Local execution

Requires `lua5.4`. The SQLite suite also requires `luasql.sqlite3` and is
skipped if it is not installed.

```bash
sh nmap/tests/run.sh
```

## Variables

| Variable | Effect |
| --- | --- |
| `CVESCANNER_STRICT=1` | XFAIL and XPASS make the run fail. Use it after fixing the known bugs. |
| `CVESCANNER_FILTER=text` | Runs only the tests whose `suite :: name` contains `text`. |
| `CVESCANNER_NSE=path` | Script under test (default `nmap/src/cvescannerv2.nse`). |
| `LUA=binary` | Interpreter used by `run.sh` (default `lua5.4`). |

```bash
docker run --rm -e CVESCANNER_FILTER=openssl cvescannerv2-tests
```

## Packaging tests

Two checks of the scanner image packaging:

- Static (`lua/test_docker.lua`, suite `docker packaging`): no Docker needed.
  Checks that every `data/` file read by the NSE is copied or generated by
  `docker/Dockerfile`, that the `COPY data/...` paths exist and are not excluded
  by `.dockerignore`, and that the default URL in `scripts/download-catalog.sh`
  matches `ARG CATALOG_BASE` in `docker/Dockerfile`. Takes less than one second
  and runs inside `sh nmap/tests/run.sh`.
- Integration (`docker/check.sh [--fresh]`): requires Docker and network access.
  Builds the `nodb` and `db` images, checks their contents, validates `cve.db`
  with `python3`, and scans a `php:5.6-apache` on a temporary network. It is not
  part of `run.sh`. Takes several minutes (the first time, longer because of the
  database and catalog download). `--fresh` forces regenerating the database and
  the catalog without cache. Prints `PASS`/`FAIL` per check and returns a non-zero
  exit code if any check fails. Cleans up containers, network and temporary
  files when it finishes.

```bash
sh nmap/tests/run.sh                     # static, no Docker
sh nmap/tests/docker/check.sh            # integration
sh nmap/tests/docker/check.sh --fresh    # integration without cache
```

`lua5.4 nmap/tests/lua/run.lua` (387 cases) is higher because some cases
are generated in loops (for example, `compare_version`).

## Results

- `PASS`/`FAIL`: the behavior must be kept.
- `XFAIL`: a known bug is still present. The test describes the
  correct behavior and shows the reason for the failure.
- `XPASS`: a known bug no longer reproduces. Change the `known_bug` test to
  `case`.

Without `CVESCANNER_STRICT`, `XFAIL` does not make the run fail. This way the
suite works as a regression suite from now on and as a checklist for the fixes.

## How the loader works

`harness.load_scanner()` loads `cvescannerv2.nse` with `load()` and returns its
entry points: `portaction`, `preaction`, `postaction` and `portrule`. The NSE
libraries are replaced with stubs, which are kept in `scanner.stubs`.

The modules in `nmap/src/cvescannerv2/**.lua` are loaded with `require()` and
accessed as `scanner.modules.<name>`, where `<name>` is the last component of
the module (for example, `scanner.modules.service_cves` or
`scanner.modules.state`). The snapshot is taken at load time, so each scanner
keeps its own modules even if another one is loaded later. Nothing is copied to
the scanner table: the tests call the same functions that Nmap uses, without
aliases or test-only exports.

`lua/test_architecture.lua` enforces the layer graph: a module can only `require`
modules from a strictly lower layer, and there are no cycles. It also fixes the
owners of the Nmap and I/O APIs (`get_script_args` only in `config`, `luasql` only
in `db`, `io.open` only in `util`, `catalog.store`, `reference_files`, `log` and
`json_report`). If a new module needs one of these APIs, it must be added to the
corresponding rule in that file.

## LSP gate (lua-language-server)

Checks the Lua diagnostics with the VS Code server. It must give 0
diagnostics: `check.json` must end with an empty list. The configuration
is in `.luarc.json`.

```bash
LLS=~/.vscode/extensions/sumneko.lua-3.19.2-linux-x64/server/bin/lua-language-server
$LLS --check="$PWD" --configpath="$PWD/.luarc.json" --checklevel=Hint --check_format=json --logpath=/tmp/lls
lua nmap/tests/lua/run.lua
```
